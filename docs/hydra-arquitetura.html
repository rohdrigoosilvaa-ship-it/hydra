01

Arquitetura geral do sistema

Uma API central, stateless, servindo um SPA e processos assíncronos — sem lógica de negócio no cliente.

O Hydra é uma aplicação web-first: um SPA React consome uma API REST única (NestJS), que é a única porta de entrada para o banco de dados, o armazenamento de arquivos e as integrações externas. Nenhuma regra de negócio roda no cliente além de validação de formulário — isso mantém o isolamento multi-tenant e as permissões garantidos num único ponto.

Três características guiam essa topologia:

  • Stateless na API — nenhuma sessão em memória local; qualquer instância pode responder qualquer requisição, o que permite escalar horizontalmente sem sticky sessions.
  • Assíncrono onde o usuário não deveria esperar — envio de evento eSocial, geração de PDF de laudo, disparo de notificação em massa: tudo vai para fila, não bloqueia a resposta HTTP.
  • Um adaptador para cada dependência externa — storage, e-mail, SSO e eSocial ficam atrás de interfaces internas, para trocar provedor sem reescrever módulos de negócio.
02

Arquitetura de pastas

Monorepo com pnpm + Turborepo: um pacote de tipos e um de UI compartilhados entre web, API e worker.

Diferente do Portal SSMA atual (dois projetos soltos, client/ e server/), o Hydra nasce como monorepo — necessário porque worker, API e web vão compartilhar tipos (DTOs) e componentes de UI desde o primeiro módulo.

hydra/ ├── apps/ │ ├── web/ React + Vite — SPA principal (colaborador, gestor, admin) │ ├── api/ NestJS — API REST, guards de tenant/RBAC, módulos de domínio │ └── worker/ BullMQ — jobs assíncronos (eSocial, relatórios, notificações) ├── packages/ │ ├── ui/ Hydra UI — design system (componentes, tokens, ícones) │ ├── types/ DTOs e enums compartilhados (gerados a partir do schema) │ ├── db/ schema.prisma, migrations, seed, client Prisma │ └── config/ eslint, tsconfig, tailwind preset, prettier — base única ├── docs/ ADRs e este documento de arquitetura ├── turbo.json ├── pnpm-workspace.yaml └── .env.example

Dentro de apps/api, cada módulo de negócio (PGR, EPI, Treinamentos...) é uma pasta autocontida — controller, service, DTOs e testes — registrada no módulo raiz. Isso segue diretamente a regra do item 57 do escopo: "cada módulo deve ser independente, mas integrado ao núcleo".

apps/api/src/ ├── core/ tenant middleware, auth guards, audit interceptor ├── modules/ │ ├── org/ tenants, companies, branches, units, employees │ ├── pgr/ │ ├── epi/ │ ├── trainings/ │ ├── checklists/ │ ├── actions/ │ └── ... um por módulo do mapa de telas (seção 10) └── main.ts
03

Stack tecnológica

TypeScript ponta a ponta. Escolhas otimizadas para um time pequeno mantendo um produto com muitos módulos.

Front-end

  • React 18 + TypeScript, Vite
  • Tailwind CSS + componentes próprios (Hydra UI, base Radix)
  • TanStack Query (dados do servidor) + Zustand (estado local leve)
  • React Hook Form + Zod (formulários e validação)
  • Recharts (gráficos), Lucide (ícones), Framer Motion (transições)

Back-end

  • Node.js + TypeScript, NestJS (módulos, DI, guards)
  • PostgreSQL 16 + Prisma ORM
  • Redis (cache, filas, rate limit) + BullMQ (jobs)
  • Zod/class-validator na borda da API
  • OpenAPI gerado automaticamente a partir dos DTOs

Autenticação & identidade

  • JWT de acesso (15 min) + refresh token rotativo (cookie httpOnly)
  • Argon2 para hash de senha
  • TOTP para MFA · OIDC para SSO (Microsoft Entra ID)

Infraestrutura

  • Storage S3-compatível (Cloudflare R2 por custo; AWS S3/Azure Blob via adaptador)
  • PgBouncer (pool de conexões)
  • Observabilidade: logs estruturados + tracing (OpenTelemetry)

Por que NestJS em vez de Express puro: o número de módulos de negócio previsto (mais de 30) exige uma convenção forte de organização, injeção de dependência e guards reaproveitáveis — é exatamente o que o Express simples do Portal SSMA atual começou a sentir falta ao crescer. NestJS resolve isso sem sair de Node/TypeScript.

Modelo de banco de dados

Um schema Prisma único, organizado por domínio; toda tabela de negócio carrega tenantId.

Três convenções valem para toda tabela do domínio, sem exceção — elas são o que torna o multi-tenant (seção 06) e a auditoria (seção 14) possíveis sem gambiarra depois:

tenantId
chave estrangeira obrigatória para companies — nunca nula, sempre indexada.
createdAt / updatedAt / deletedAt
soft delete por padrão; exclusão definitiva é ação administrativa separada, auditada.
createdById / updatedById
rastreabilidade de quem alterou, exigida pelo item 39 (auditoria).

06

Estratégia multi-tenant

Banco compartilhado com isolamento por linha, reforçado no próprio PostgreSQL — não só na aplicação.

Para o MVP e a maioria dos clientes, o Hydra usa um único banco PostgreSQL, schema compartilhado, com toda tabela de negócio carregando tenantId. É o modelo mais barato de operar (uma migração, um backup, um monitoramento) — mas ele só é seguro se o isolamento não depender exclusivamente de "lembrar de filtrar" no código.

Por isso, o isolamento tem duas camadas independentes:

  1. Aplicação — um middleware de tenant lê o tenantId do JWT e injeta automaticamente o filtro em toda query do Prisma (via extension), sem depender de cada desenvolvedor lembrar de escrever WHERE tenantId = ....
  2. Banco de dados — Row-Level Security (RLS) nativo do PostgreSQL, com uma policy por tabela que só libera linhas cujo tenant_id bate com a variável de sessão definida na conexão. Mesmo uma query com bug na camada 1 não vaza dado de outro tenant.

Usuários que atendem mais de uma empresa — caso típico de consultorias de SST e prestadores — têm múltiplos vínculos de tenantId associados ao mesmo login, com um seletor de empresa ativa na interface; trocar de empresa reemite o JWT com o novo tenantId.

07

Estratégia de autenticação

JWT curto + refresh rotativo como padrão; MFA e SSO corporativo previstos desde o modelo de dados.

Senha
hash Argon2id, nunca reversível, nunca logada.
Access token
JWT de 15 minutos, carrega userId, tenantId ativo e papéis — enviado em header Authorization.
Refresh token
opaco, 30 dias, rotacionado a cada uso, guardado com hash no banco (revogável individualmente), entregue em cookie httpOnly + secure + sameSite=strict.
MFA
TOTP (RFC 6238) por usuário, com opção de tornar obrigatório por tenant — tabela mfa_secrets e códigos de recuperação de uso único.
SSO / OAuth
camada OIDC genérica; primeiro provedor suportado é Microsoft Entra ID, por já ser o ecossistema corporativo do usuário-tipo do Hydra.
Nota: nenhuma dessas peças precisa estar pronta no MVP — mas o modelo de dados (tabela users com authProvider, tabela separada de mfa_secrets) já nasce preparado, para não exigir migração destrutiva quando forem ligadas na Fase 3.
08

Estratégia de permissões

RBAC com escopo: o mesmo papel se comporta diferente conforme a abrangência do vínculo.

Um papel sozinho não basta — "Gestor SST" da filial Santarém não pode enxergar dados da filial Vila do Conde. Por isso cada vínculo de permissão é a combinação de papel + escopo: (userId, tenantId, role, scopeType, scopeId), onde scopeType é company, branch ou unit.

  • SUPER_ADMIN plataforma Hydra
  • ADMIN_EMPRESA todas as filiais
  • GESTOR_SST escopo configurável
  • ENGENHEIRO escopo configurável
  • TECNICO_SST escopo configurável
  • MEDICO dados de saúde, escopo próprio
  • ENFERMEIRO dados de saúde, escopo próprio
  • RH escopo configurável
  • GESTOR unidade/setor
  • COLABORADOR somente os próprios dados
  • PRESTADOR só serviços/clientes vinculados
  • CLINICA só atendimentos próprios
  • FINANCEIRO módulo financeiro
  • COMERCIAL módulo CRM
09

Design system — Hydra UI

Tokens antes de componentes: cor, espaço e tipografia definidos uma vez, consumidos por Tailwind e pelos componentes React.

Identidade própria, não copiada de nenhum produto de referência: paleta em petróleo/teal (tecnologia, saúde, controle) com âmbar reservado exclusivamente para estados de atenção e criticidade — nunca decorativo. Tipografia serifada para títulos (peso editorial, autoridade de laudo técnico) e sem serifa para corpo de texto e dados tabulares.

Componentes base

Button, Input, Select, Modal, Drawer, Card, DataTable, Badge, Tabs, Dropdown, Tooltip, Toast, Alert, Calendar, DatePicker, FileUpload, Signature, Timeline, KPI Card, Chart.

Estados obrigatórios

Todo componente de dado precisa de: loading (skeleton), vazio (empty state com ação), erro (com retry) — não apenas o estado "feliz". Sem isso, um módulo não é considerado pronto para revisão.

O pacote packages/ui é publicado internamente e consumido tanto pelo apps/web quanto por eventuais superfícies futuras (portal do colaborador, app mobile) — garantindo que "parecer Hydra" seja automático, não uma checklist manual por tela.

Fluxo de navegação

Do login ao dado — o caminho mais curto sempre visível, o resto a um clique.

Login └─ (múltiplos tenants?) → Seletor de empresa └─ Dashboard (Control Center) ├─ Card de pendência → lista filtrada do módulo → registro → ação ├─ Sidebar → módulo → sub-área → registro └─ Busca global (Ctrl+K) → qualquer entidade → registro direto

Regra de UX: todo card do dashboard e todo alerta é clicável e leva direto à lista já filtrada — nunca a uma tela genérica que o usuário precisa refiltrar manualmente.

Estratégia de segurança

Auditoria imutável, menor privilégio por padrão, segredos fora do repositório.

  • Audit log — toda escrita relevante (criação, alteração, exclusão, download, exportação, login) grava em audit_logs com usuário, IP, timestamp e diff; a tabela é apenas-inserção, sem update/delete pela aplicação.
  • Exclusão — soft delete por padrão (item 39); exclusão física é ação restrita a SUPER_ADMIN, exigindo confirmação e motivo registrado.
  • Segredos — nunca em .env versionado; gerenciador de segredos (Doppler ou equivalente do provedor de hospedagem) por ambiente.
  • Transporte e repouso — TLS obrigatório ponta a ponta; criptografia de disco no provedor; campos de saúde especialmente sensíveis (CID, diagnóstico) com criptografia de coluna adicional.
  • Limites — rate limiting por tenant e por IP no gateway da API; validação de payload (Zod/class-validator) rejeitando por padrão o que não é explicitamente esperado.
15

Estratégia LGPD

Classificação de dados desde a modelagem, não como camada adicionada depois.

Classificação
toda tabela é marcada como pública, interna, pessoal ou pessoal sensível (dado de saúde) já no schema — não é decisão de código, é metadado consultável.
Acesso a dados sensíveis
tabelas de saúde (medical_records, asos, pcmso) exigem papel específico (Médico/Enfermeiro) mesmo dentro do próprio tenant — Gestor de SST não vê diagnóstico, só validade de exame.
Retenção
política de retenção por tipo de entidade, com job agendado de anonimização quando o prazo legal expira.
Direitos do titular
fluxo de solicitação (acesso, correção, exportação, anonimização) com trilha própria, não um e-mail manual para o suporte.
Consentimento
tabela de registros de consentimento vinculada ao colaborador, quando aplicável (ex.: uso de imagem em treinamento).
16

Estratégia de escalabilidade

Escalar por réplica antes de escalar por reescrita — o monólito modular aguenta muito mais do que parece.

  • API stateless — múltiplas instâncias atrás de um load balancer, sem sessão em memória; escala horizontal trivial.
  • Worker separado — jobs pesados (geração de relatório, envio em massa, eSocial) escalam independente da API que atende usuários.
  • Réplica de leitura — consultas de BI/relatório apontam para uma réplica do Postgres, isolando carga analítica da transacional.
  • Cache — Redis para dados de leitura frequente e baixa mutação (estrutura organizacional, permissões resolvidas).
  • Caminho de saída para clientes grandes — se um tenant crescer a ponto de justificar isolamento físico, a migração para schema dedicado (seção 06) é um script de dados, não uma reescrita de aplicação, porque o modelo já carrega tenantId em toda tabela desde o dia um.
